# ZCode 侧插件编制计划（DRAFT，未实施）

日期：2026-09-09。授权：用户要求完成消息队列后，尝试编制 ZCode 侧插件计划。
本轮只编写计划；不安装 ZCode 插件，不创建/续跑 Codex 任务，不操作安装界面，不开放监听端口。

## 1. 目标和已具备的底座

目标：ZCode 能向用户明确绑定的已有 Codex 任务投递消息、读取回执，并将结果回送至原 ZCode 任务；最终验证无需模型主动轮询的事件触发。
不把“启动一个独立 codex exec 进程”当作“控制用户当前桌面上的 Codex 任务”。不把落盘、投递、模型回应、原生完成与业务验收混为一谈。

本轮已完成 Codex 侧持久队列：任务 FIFO、队伍标签汇总、唯一消息标识关联、失败隔离和不盲重发。后续精简为 8 个默认工具：单条/批量共用 send，后台按需启动、空闲退出、显式 pause/resume，read 同时支持对话和收件箱。
实际回传测试收到 QUEUE_OK_1、QUEUE_OK_2；第二条由后台在第一条确认结束后派发。
但这是 Codex → ZCode → 本地收件箱，不是 ZCode 主动唤醒 Codex。后续应复用消息标识、事件游标、状态语义，不先抽象成多智能体框架。

## 2. 构建指南及证据等级

[指南原文](../docs/zcode-plugin-guide-reported.md) 来自会话「审查zcodeops计划可行性与安全性」
`sess_364f3d09-4b3d-4db4-811f-3624dde5a68f`，消息 `msg_mttu6f7n_86f283e7-cd64-4e75-9e20-0469b99d74b0`。
已完整读取，以下 ZCode 契约为该智能体的调研结果，不升级为本插件的独立实测事实：

- 首选清单 `.zcode-plugin/plugin.json`；可挂载 skills、commands、hooks、MCP、agents。核心候选是 Node/stdio MCP 加少量命令/技能。
- Hook 候选为 SessionStart、UserPromptSubmit、Stop；不依赖未支持的 SessionEnd。
- Windows 使用 process 类型 command+args，避免 shell 拼接。Hook 只做有界收发/上下文注入，不在内联 Hook 中等待模型完成。
- 持久状态候选位置 ZCODE_PLUGIN_DATA；transcript_path 是临时文件，不可作为后续后台数据源。
- 敏感 userConfig 存储能力存在限制；不把 Sharing Link 或认证密钥装入插件包/仓库，不绕过用户审批。
- 首次本地市场安装可能需要用户在 GUI 确认；修改后可能必须新建会话才加载 Hook/MCP。一次性安装不意味着运行时依赖 Computer Use。
- 桌面嵌入会话是否触发 Hook 尚未实测；async、agents 执行语义存在本机与在线文档冲突。Stop 续跑次数上限有调研证据，但不能当成无限后台唤醒通道。

Codex 候选依据已另外核对 [OpenAI App Server 官方文档](https://learn.chatgpt.com/docs/app-server)：
`thread/read` 可只读查看任务；`thread/resume` 加 `turn/start` 可继续已有任务；事件通知提供消息增量和回合变化。
这证明协议能力，不证明新启动的独立 App Server 能安全接管本机正在运行的桌面任务。宿主连接、任务所有权、配置/审批上下文与 UI 可见性必须实测。
[非交互模式官方文档](https://learn.chatgpt.com/docs/non-interactive-mode) 也提供 `codex exec resume <SESSION_ID>`；本计划只将其视为独立 CLI 工作流候选，不作为桌面控制已成立的证据。

## 3. 最小候选结构与消息契约

候选目录：ZCode 独立插件根下的 `.zcode-plugin/plugin.json`、`.mcp.json`、一个 Node MCP 程序、一个操作技能；只有 Hook 验证通过后才加入 hooks 配置。
不要先创建空骨架、安装市场或复制现有整个 Codex 插件。

先做三种能力：列出已授权绑定、向指定绑定入队、读取该绑定的事件。绑定至少包括来源 ZCode session、目标 Codex task、允许工作目录、teamId 与有效期；不得从模型正文推断接收人或自动扩大范围。
消息含稳定 messageId、来源、目的地、teamId、replyTo 与正文；接收事件保留原始角色/来源，不伪装成人类新指令。
同目标任务有序，跨任务独立，队伍只汇总；同一事件最多投递一次，失败结果不明先核对，不自动广播或循环回送。
只为显式绑定提供数据访问；不允许 ZCode 插件直接遍历全部 Codex 聊天或任意读取当前队列 SQLite 文件。

当前 SQLite 队列专用于 native sess_ 目标，不能把 Codex ID 塞进去冒充已支持。反向通道在验证真实目标后增加最小独立适配；协议复用优先于强行共用表。

## 4. 实施顺序与验收门

### P0：确认宿主接口（先只读）

1. 记录用户当前 ZCode 桌面/内嵌 CLI 版本，并取得指南所用官方文档链接，核验最小 manifest/Hook stdin/stdout。
2. 对用户明确选择的既有 Codex 测试任务，核验本地可访问控制通道、真实 taskId、工作目录和原生状态；不得直接向业务任务发送。
3. 把独立 CLI 和实际桌面连接分开标记。如果只有独立 CLI 可用，报告能力缺口，不以新进程替代目标任务。

验收：形成精确接口/版本/响应证据，确认权限边界；无法证明桌面目标映射则停在只读，不进入自动写入。

### P1：最小插件加载与 Hook 探针

经用户另行授权后，创建最小清单/MCP；首次安装由用户确认本地市场。探针只记录事件名、sessionId、来源和时间，不保存原始敏感 transcript。
验证同一安装版本在新会话和已有桌面会话的加载差异；分别触发 SessionStart、UserPromptSubmit、Stop。
不依赖 async；不采用 Stop block 作为消息到达时的通用唤醒方式。

验收：桌面产生真实 Hook 事件且不会阻塞/修改用户操作；若旧会话不能生效，明确需要新会话，不能声称热更新可用。

### P2：用户触发的反向往返

ZCode MCP 入队 → 用户绑定的 Codex 测试任务收到消息 → 原生回复/完成事件 → ZCode 收件箱。
先只测试一条禁止工具/文件修改的固定回复，再测试两任务并发、同任务 FIFO、重复入队、断线和进程重启。
严禁未经确认更换模型、工作目录、沙箱或批准权限；不直接补写桌面索引和对话数据库。

验收：两端原生消息可见，ID 映射和回执完整；独立 CLI 成功但桌面无对应任务不通过本门。

### P3：事件驱动回送和唤醒

在 P2 通过后，选择真实支持的宿主通知/调度通道。Hook 可采集结果，但没有新回合就可能不触发；此时需要单独的唤醒路径，不用 Stop 续跑循环填补。
仅在已授权绑定内唤醒，设置防回环标识、单事件消费、次数/过期限制和显式停用；无变化保持静默。

验收：没有用户新消息、没有 Codex 模型轮询时，ZCode 新事件能触发指定任务且只触发一次。缺少可验证入口则标记为“已落盘，未唤醒”。
